# Audit complet — BâtiBénin (2026-08-09)

Audit de l'état réel du code, de la base de données et du produit, suivi d'un plan
d'exécution étape par étape pour atteindre l'objectif : **le SaaS construction le plus
complet du marché africain, tout en restant simple d'utilisation.**

types régénéré ; à exclure du lint car auto-généré.

## 2. 🚨 Problème critique n°1 : dérive base de données ↔ code

La base contient **13 tables**. Le code en interroge **46**.

**Tables présentes** : `audit_logs`, `budget_lines`, `categories`, `companies`,
`demo_requests`, `expenses`, `payments`, `profiles`, `projects`, `quotes`, `site_logs`,
`suppliers`, `user_roles`.

**Tables manquantes (33)** : `carts`, `cart_items`, `deliveries`, `dispute_evidences`,
`disputes`, `documents`, `drivers`, `invoice_items`, `invoice_payments`, `invoices`,
`material_deliveries`, `material_requirements`, `materials`, `messages`,
`notification_preferences`, `order_items`, `orders`, `organizations`,
`payment_transactions`, `photos`, `plans`, `product_categories`, `product_inventory`,
`product_prices`, `products`, `project_members`, `provider_reviews`, `providers`,
`quote_bids`, `quote_items`, `quote_requests`, `refunds`, `reserves`, `stores`, `tasks`.

**Également manquants** : les RPC `get_shared_project` et `get_payment_link_order`, les
buckets de stockage `documents` et `demo-attachments` (seul `journal-photos` existe),
et les colonnes ajoutées après coup (`payments.due_date`, `payments.provider`,
`payments.status`, `demo_requests.attachment_name`, `follow_up_date`…).

**Conséquence concrète** : sur les 35 pages de l'application, **une vingtaine renvoie
une erreur ou une page vide en production** (marketplace, commandes, panier, boutique,
documents, plans, photos, tâches, réserves, messages, matériaux, facturation, litiges,
demandes de devis, prestataires, partage public, paiement mobile money).

**Cause** : 12 migrations existent dans `supabase/migrations/` mais ne sont pas
appliquées à l'instance (remix / réinitialisation de la base).

**Correctif** : rejouer dans l'ordre les migrations `20260810000000` → `20260821000000`,
recréer les buckets, puis régénérer `types.ts`. C'est **l'étape 0, bloquante, de tout
le plan** : aucune nouvelle fonctionnalité n'a de sens tant que 60 % de l'app ne
fonctionne pas.

## 4. Plan d'exécution étape par étape

Chaque étape est livrable indépendamment et se termine par
`npm run build` → `tsc --noEmit` → `eslint .` → `npm run test` + mise à jour de la doc.

### Étape 0 — Remise en service (bloquant, ~1 lot)

1. Rejouer les 12 migrations manquantes dans l'ordre chronologique.
2. Recréer les buckets `documents` (privé) et `demo-attachments` (privé) + politiques.
3. Recréer les RPC `get_shared_project` et `get_payment_link_order`.
4. Régénérer `src/integrations/supabase/types.ts`, exclure ce fichier d'ESLint,
   lancer `npm run format`.
5. **Critère de sortie** : 0 erreur `tsc`, 0 erreur lint, les 35 pages s'ouvrent sans
   erreur console.

### Étape 1 — Fiabilité et confiance dans les données

1. Test de fumée automatisé qui ouvre chaque route et échoue sur erreur console.
2. Garde-fou CI : un test qui compare la liste des tables interrogées par le code à
   celle de la base (empêche la dérive de se reproduire).
3. États vides soignés + états d'erreur explicites sur les 35 pages.
4. Page « Santé du compte » : quotas, stockage utilisé, export de toutes ses données.

### Étape 2 — Simplicité d'usage (le vrai différenciateur)

1. **Refonte de la navigation** : regrouper les 35 entrées en 6 univers — *Chantier*,
   *Finances*, *Achats*, *Équipe*, *Documents*, *Pilotage* — avec menu latéral repliable
   et barre de commande (⌘K) déjà présente à généraliser.
2. **Accueil par rôle** : écran d'accueil différent pour particulier / maître d'œuvre /
   entreprise / vendeur, avec 3 actions prioritaires seulement.
3. **Modèles de chantier prêts à l'emploi** : « Villa basse 3 ch. », « R+1 », « Duplex »,
   « Boutique » — budget, postes et tâches pré-remplis en un clic.
4. **Bibliothèque de prix de référence** (ciment, fer, sable, main-d'œuvre) par ville,
   alimentée par les dépenses agrégées et anonymisées de la plateforme.
5. **Saisie express mobile** : 1 écran, 3 champs, photo du reçu, fonctionne au pouce.

### Étape 3 — Terrain et faible connexion

1. Cache local (IndexedDB) des données du chantier actif + persistance TanStack Query.
2. File de synchronisation différée pour dépenses, journal, photos, tâches.
3. Compression des images avant envoi, upload en arrière-plan avec reprise.
4. Indicateur clair « hors ligne / n éléments en attente » dans l'en-tête.

### Étape 4 — Notifications multi-canal

1. Tables `notifications` (persistée, temps réel) et `device_tokens`.
2. Centre de notifications unifié remplaçant la cloche actuelle.
3. E-mails transactionnels de marque (domaine d'envoi à configurer) : alertes budget,
   échéances, devis reçu, commande expédiée, digest hebdomadaire.
4. WhatsApp et SMS pour les événements critiques (lien de paiement, livraison, devis).
5. Préférences fines par canal et par type d'événement.

### Étape 5 — Monétisation

1. Tables `plans`, `subscriptions`, `invoices_saas`, `commissions`.
2. Offres : **Gratuit** (1 chantier), **Pro** (chantiers illimités, exports, membres),
   **Entreprise** (multi-chantiers, organisation, API), **Vendeur** (commission sur ventes).
3. Limites d'usage appliquées côté base (RLS + fonctions) et non seulement côté UI.
4. Encaissement réel : MTN MoMo / Moov Money via PayDunya ou équivalent, plus carte.
5. Page de tarifs publique, essai 14 jours, relances d'impayés, tableau de bord revenus.

### Étape 6 — Marketplace de confiance

1. Workflow de vérification des comptes (dépôt de pièces, validation admin, badge).
2. Avis vérifiés adossés à une commande réelle, réponse du vendeur, signalement.
3. Séquestre des paiements jusqu'à confirmation de livraison, relié aux litiges.
4. Classement vendeurs : délai de livraison, taux d'annulation, note.

### Étape 7 — Intelligence

1. **Métré assisté** : à partir de la surface et du type de maison, estimation des
   quantités (ciment, fer, agglos, sable) et du budget par poste.
2. **Assistant conversationnel** par rôle, avec actions (créer une dépense, chercher un
   prestataire, comparer des prix).
3. **Notes vocales** sur le journal de chantier (transcription automatique, FR + langues locales).
4. **Détection d'anomalies** : dépassement de poste, prix anormalement élevé, retard prévisible.
5. **Rapport hebdomadaire automatique** envoyé au maître d'ouvrage.

### Étape 8 — Expansion

1. Location de matériel (`equipment`, `equipment_rentals`) : tarif jour/semaine, caution.
2. Immobilier promoteurs : programmes → immeubles → lots, ventes et réservations.
3. Cartes et géolocalisation : rayon de livraison, chantiers et fournisseurs à proximité.
4. Application mobile Expo réutilisant la couche de données.
5. API publique et webhooks pour les entreprises.

### Étape 9 — Exploitation

1. Analytics produit (activation, rétention, entonnoirs) et suivi d'erreurs.
2. Journalisation d'audit étendue à toutes les tables sensibles.
3. Sauvegardes, export/suppression de compte, page de conformité.
4. Documentation utilisateur intégrée, centre d'aide, visites guidées contextuelles.

## 5. Priorisation recommandée

| Priorité | Étapes | Pourquoi |
| --- | --- | --- |
| 🔴 Immédiat | 0, 1 | L'application est aujourd'hui majoritairement non fonctionnelle |
| 🟠 Court terme | 2, 3 | « Le plus complet » ne sert à rien s'il n'est pas utilisable sur chantier |
| 🟡 Moyen terme | 4, 5, 6 | Rétention puis revenus |
| 🟢 Long terme | 7, 8, 9 | Différenciation et expansion |

**Règle directrice** : à chaque nouvelle fonctionnalité ajoutée, une simplification doit
être livrée en parallèle (regroupement, valeur par défaut intelligente, automatisation).
C'est la seule façon de tenir les deux objectifs — le plus complet **et** le plus simple.
